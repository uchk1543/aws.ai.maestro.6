# B4-L0 요구사항: OCR 원본(l0) 저장과 비용 줄이기

담당: 4번 서버. 관련: F10 (#194), 판독 캐시 B3 (#124), agent-design.md 2·4번.

## 배경
파이프라인을 l0(OCR 전체 파싱) → l1(필요한 칸) → l2(핵심 칸 정합) → l3(카드)로 나눠 보라는 피드백을 받았다.
지금 코드는 l1(`read_document`), l2(`cross_check`·`reread_field`), l3(`finish_report`)가 있고, l0은 F10의 Textract OCR이 맡는다.
남은 빈틈은 세 가지다.
- 작업 줄의 `ocr` 칸은 DynamoDB 400KB 한도 때문에 서류당 600줄에서 잘린다.
- 같은 파일도 매번 Textract를 부른다. 판독 캐시는 배포 환경에서 꺼져 있다(`READ_CACHE_BUCKET` 없음).
- 서류마다 Bedrock을 두 번(분류·판독) 부른다. Textract는 이미 매번 부르고 있다.

## 요구사항
1. 자르지 않은 OCR 결과를 S3 `cache/ocr/`에 저장하고, 같은 파일이면 Textract를 다시 부르지 않는다.
2. 저장소 오류나 빈 결과가 OCR·작업을 막거나 영구히 남지 않는다.
3. 서류 분류는 Textract 제목 줄로 할 수 있고, 확신이 없으면 Bedrock으로 분류한다. 기본은 끈다(팀 결정 전).
4. Textract 계정 한도(서울 동기 API 초당 1건) 때문에 OCR이 조용히 빠지지 않는다.
5. 같은 서류를 다시 올리면 Bedrock 판독을 부르지 않는다(판독 캐시). 라이브 데모·반복 측정은 `NO_CACHE=1`로 끈다.
6. 읽기를 Textract로 옮기는 것은 측정으로 정확도를 보이고, 팀이 정하기 전에는 코드로 만들지 않는다(나중).

## 받아들이는 기준
- 단위 테스트(AWS 호출 없음) 전체 통과.
- 개발용 서류에서 Textract 분류가 Bedrock 분류(B1 #86, 288/288)보다 나쁘지 않다.
- 배포 뒤: 같은 서류를 두 번 올리면 두 번째 작업 로그에 `저장분 사용`, `[cache] read hit`가 찍힌다.
