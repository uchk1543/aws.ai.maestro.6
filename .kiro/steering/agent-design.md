# 에이전트 설계 규칙: 읽기는 AI, 판정은 코드

에이전트 · 검증 · 평가 코드를 짤 때 따르는 규칙이다. AI 담당이 관리하고, 바꾸기 전에 팀에 알린다. 데이터 형식은 docs/schema.md 를 따른다.
대상 서류는 과제 원문의 B/L · 상업송장 · 포장명세서 · 원산지증명서 · 통관 신고서다. 칸 이름은 예시다.
이 파일은 agent/ · tools/ · eval/ · Spec 파일을 다룰 때 읽힌다. Spec 을 처음 만들 때는 아직 Spec 파일이 없어 자동으로 읽히지 않으니, 채팅 입력창에서 # 으로 이 파일을 직접 붙인다.

**먼저 지킬 것:** 이 파일은 다 만든 모습이다. 한 번에 다 만들라는 뜻이 아니다. 구현은 0번 순서를 따르고, 지금 단계(처음에는 P0)에 없는 항목은 코드로 만들지 말고 tasks.md 에 '나중'으로만 적는다.

## 과제 기능과 이 파일의 대응

| 과제 기능 | 도구 | 섹션 |
|---|---|---|
| ① OCR · 핵심 항목 추출 | read_document, ocr_document | 2, 4 |
| ② 종류 분류 · 교차 검증 | classify_document, cross_check, reread_field | 1, 2, 3, 4 |
| ③ HS 추천 · 통관 서류 작성 | recommend_hs, draft_declaration | 6, 7 |
| ④ WMS/TMS/ERP 연동 | push_to_wms (코드가 부름, 에이전트 도구 아님) | 8 |
| ⑤ 자연어 현황 조회 | query_shipments | 9 |

자동이 기본이고, 사람은 Agent 가 넘긴 예외만 본다. 문제없는 건은 업로드부터 WMS 등록까지 사람 손 없이 끝난다.

## 0. 만드는 순서

24시간 안에 다 만들 수 없다. 앞 단계가 끝까지 돌기 전에 다음 단계를 시작하지 않는다. 다섯 기능은 모두 데모에 한 장면씩 나와야 하므로 P1 까지는 만든다.

| 단계 | 언제까지 | 만드는 것 |
|---|---|---|
| P0 | 금 18시 첫 배포 | 모델 호출 확인(10번), 상업송장 · 포장명세서 두 종류의 분류와 따로 읽기(raw), 대조 규칙 3개(행 맞추기 없이 서류 전체 값만. 예: 총수량 · 총중량 · 송장 번호. 고르는 것은 관세 규칙 담당), 등급 셋, 근거 문장틀, 정답지 채점 |
| P1 | 토 02시 | B/L · 원산지증명서 추가, Textract OCR 확인, 다시 확인, 서류 한 장 안 계산 규칙, 행 맞추기, HS 추천과 자동 확정(확정 이력), 신고서 초안, 가상 WMS 자동 등록, 현황 조회, 판독 캐시, 모델 단독 기준선, 10회 반복 측정 |
| P2 | 여유가 있을 때 | 칸만 잘라서 다시 읽기, 원산지 규칙 심화, 관세율 조회, 실제 시스템 연동 |

시간이 모자라면 ERP 용 CSV → 원산지증명서 대조 → 신고서 PDF(화면 표로 대신) → 모델 단독 기준선 순서로 뺀다. 기능 ③④⑤ 가 한 장면씩 도는 것은 빼지 않는다.

## 1. 순서는 코드가 지키고, 판단은 에이전트가 한다

- 에이전트는 두 개다. 문서 처리 Agent(기능 ①②③)와 현황 조회 Agent(기능 ⑤). 시스템 프롬프트와 도구 목록을 따로 둔다. 기능 ④ 의 쓰기는 에이전트가 하지 않는다(8번).
- 에이전트는 도구를 고르지만, 판정 · 등급 · 근거 문장 · 신고서 칸 값 · HS 확정은 만들지 않는다. 모두 코드가 만든다.
- 문서 처리 Agent 가 정하는 것
  - 서류 종류: 자동으로 분류한다(과제 기능). 사용자는 화면에서 고칠 수 있고, 고친 값이 있으면 그 값을 쓴다. 애매하면 사람에게 묻는다.
  - 빠진 서류: 있는 서류끼리 먼저 대조하고, 빠진 서류를 요청한다.
  - 다시 확인할 칸의 순서, 사람에게 넘길 예외와 질문
- 리포트 도구(finish_report)는 아래 조건을 코드로 검사한다. 못 채우면 무엇이 빠졌는지 오류 메시지로 돌려주고, 에이전트는 빠진 도구를 부른다.
  - 올라온 서류를 모두 분류하고 읽었다
  - 마지막 읽기 뒤에 cross_check 를 돌렸다
  - 불일치 칸을 모두 다시 확인했다(reread_field)
  - 모든 품목에 recommend_hs 를 돌렸다(확정 또는 사람 확인 필요)
- 도구 호출은 모두 작업 단계 기록(약속 2 의 steps)에 남긴다. 이 기록이 화면의 진행 단계이자 발표의 "에이전트가 도구를 고르는 장면"이다.

## 2. 분류와 읽기 (classify_document, read_document)

- 분류는 읽기와 따로, 가벼운 호출로 한다. 분류 결과와 근거(제목, 특징이 되는 칸)를 단계 기록에 남긴다.
- 서류는 파일 하나씩 따로 읽는다. 다른 서류의 값을 프롬프트에 넣지 않는다. 함께 주면 모델이 값을 서로 맞춰 읽어, 찾으려던 불일치가 사라질 수 있다. 따로 읽되 동시에(병렬로) 부른다. 순서대로 부르면 서류 수만큼 시간이 늘어난다.
- 모델은 적힌 값을 그대로 옮긴다. 계산 · 비교 · 단위 환산을 시키지 않는다. 합계가 안 맞아 보여도 적힌 숫자를 그대로 적게 한다. 모델이 숫자를 합계에 맞게 고쳐 읽는 일이 있다.
- 모델은 칸마다 적힌 그대로의 문자열(`raw`)만 낸다. 쉼표 · 소수점 · 단위를 풀어 `value` 를 채우는 것은 코드다.
- 못 읽은 칸은 추측하지 않고 null 과 이유(흐림 · 가려짐 · 칸 없음)를 남긴다. 모델이 스스로 매긴 확신 점수는 판정에 쓰지 않는다.
- 결과는 Pydantic 모델로 검증한다. 필드마다 description 에 칸 이름, 헷갈리기 쉬운 칸과의 차이, 형식 예시를 적는다.
  예: `invoice_no` 는 'Invoice No.' 칸이며 PO No · B/L No 와 다르다. `gross_kg` 는 총중량, `net_kg` 는 순중량이다.
- 형식을 받는 방법은 10번에서 첫날 정한다. 검증에 실패하면 한 번 다시 묻고, 그래도 실패하면 '확인 필요(읽기 실패)'로 남긴다.
- 시스템 프롬프트에 오늘 날짜를 한국 시간(Asia/Seoul)으로 넣는다. 모델이 올해를 잘못 알아 최근 날짜를 미래로 볼 수 있다. Lambda 시계는 UTC 라서 자정부터 09시까지는 날짜가 하루 전으로 나온다. 날짜 비교도 코드가 한국 시간으로 한다.
- 읽은 결과는 `파일 해시 + 모델 ID + 지시문 버전(Pydantic 스키마 포함)` 을 키로 S3 나 DynamoDB 에 저장하고, 키가 같으면 저장된 결과를 쓴다. Lambda 의 /tmp 는 호출 사이에 남는다는 보장이 없다. 데모를 재현할 수 있고, 규칙만 고쳤을 때 모델 호출 없이 다시 채점할 수 있다.
- 캐시를 끄는 옵션(`no_cache`)을 둔다. 반복 측정과 라이브 데모는 캐시를 끄고 돌린다.

## 3. 판정 (cross_check)

- 규칙은 표로 둔다. 열: `rule_id`, 설명, 대상 서류와 칸, 비교 방식, 허용 오차, 등급, 근거 문장틀.
- 규칙은 3층이다.
  1. 서류 한 장 안 계산: 수량 × 단가 = 금액, 행의 합 = 합계, 순중량 ≤ 총중량, 컨테이너 번호 체크 디지트(ISO 6346)
  2. 서류끼리 같은 값: 품목 · 수량 · 중량 · 금액 · HS 코드, 원산지증명서는 품명 · HS · 수량 · 원산지가 상업송장과 맞는지, B/L 선적일 뒤에 입항일이 오는지
  3. 외부 기준(공공 데이터): HS 부호 표에 있는 코드인지, HS별 표준 수량 · 중량 단위와 맞는지(HS부호 파일의 단위 코드), 업체 부호
- 관세 규칙은 관세 규칙 담당이 조사해 표에 넣는다. 한 줄마다 출처(법령, 관세청 자료)를 적는다. 기업 수입 시나리오에 맞지 않는 규칙(예: 개인 직구 150달러 면세)은 넣지 않는다.
- 비교하기 전에 정규화한다. 정규화 표는 코드 옆에 파일로 둔다.
  - 단위 이름: CTNS = CTN = CARTON = 박스, PCS = EA
  - 단위 환산: LBS → kg
  - 품명: 대소문자, 공백, 기호를 맞춘다
- 허용 오차는 규칙마다 정한다. 예: 금액은 통화 최소 단위(USD 0.01), 중량은 반올림 단위(0.1kg). 허용 오차 안의 차이는 '참고'다.
- 서류끼리는 합계(총수량 · 총중량 · 총금액)를 먼저 비교하고, 행 단위 비교는 그다음에 한다.
- 행은 짝을 지은 뒤 비교한다. 짝짓는 순서: 품목 코드 → 정규화한 품명 → 행 순서. 짝이 안 맞거나 행 수가 다르면 '확인 필요(행 대응 안 됨)'.
- HS 코드는 서류마다 자릿수가 다를 수 있다(예: 송장 6자리, 신고서 10자리). 짧은 쪽 자릿수까지만 비교한다.
- 같은 칸을 셋 이상의 서류가 가지면 다수결로 다른 쪽을 짚는다(`suspect`). 예: 상업송장 · 선하증권 6,250kg, 포장명세서 6,520kg 이면 포장명세서. 둘뿐이면 두 칸을 함께 짚는다.
- 등급은 셋이다.
  - 불일치: 계산이나 대조로 확정되는 것만
  - 확인 필요: 값을 못 읽음, 다시 읽어야 맞음, 두 근거가 다름, 외부 조회 실패, 행 대응 안 됨, 정규화 뒤에도 남은 품명 차이
  - 참고: 화면에는 보이지만 등급을 올리지 않는다. 예: 정규화로 맞춰진 표기 차이, 허용 오차 안의 차이
- 빈 값 · 칸 누락 · 파싱 실패 · 모델 호출 실패를 '일치'로 세지 않는다. 확인 필요나 작업 실패로 남긴다.
- 외부 API 가 타임아웃이면 그 규칙만 '확인 필요(조회 못 함)'로 남기고 나머지 판정은 계속한다.

## 4. OCR 과 다시 확인 (ocr_document, reread_field)

- 스캔본과 사진은 Textract 로 OCR 한 결과(글자 · 표 · 좌표)를 저장해 둔다. Textract 의 한국어 지원은 글자 · 표 · 레이아웃까지다.
  우리 서류(상업송장 · 포장명세서 · B/L)는 영어라서 Forms · Queries · AnalyzeExpense(송장 전용)도 쓸 수 있다. 동기 API 는 파일 10MB, PDF 1쪽까지다.
- cross_check 가 불일치를 낸 칸만 다시 확인한다. 서류 전체를 다시 읽지 않는다. 어느 쪽을 잘못 읽었는지 모르므로 불일치에 걸린 칸을 모두 확인한다.
- 두 번째 근거는 첫 판독과 다른 방법으로 얻는다. 같은 모델에게 같은 이미지를 다시 보여 주면 같은 실수를 반복하기 쉽다. 아래 순서로, 쓸 수 있는 첫 방법을 쓴다.
  1. 텍스트 PDF: PDF 텍스트를 코드로 뽑아, 판독한 raw 가 문서에 그대로 있는지 확인한다. 모델 호출이 없다.
  2. 스캔본 · 사진: 저장해 둔 Textract 글자와 대조한다. 좌표가 있으므로 그 칸만 잘라 모델에게 다시 물을 수도 있다(P2).
  3. 위 둘을 못 쓰면 그 칸 하나만 묻는 질문으로 모델에게 두 번 묻는다.
- 결과 처리
  - 두 번째 근거가 첫 판독과 같으면 불일치를 확정한다.
  - 다르면 '확인 필요(읽기 오류 의심)'로 내린다.
  - 3번 방법으로만 확인했으면 리포트에 그렇게 표시한다(`checked_by: model_reread`). 근거의 세기를 구분하기 위해서다.

## 5. 근거와 리포트

- 불일치와 확인 필요마다 `rule_id`, 서류, 칸, raw, 근거 문장, 확인 방법(`checked_by`)을 붙인다.
- 근거 문장은 규칙의 문장틀로 코드가 만든다. 예: "상업송장 1행 총중량 6,250kg과 포장명세서 6,520kg이 다릅니다."
- 모델에게 요약을 맡길 때는 issues 목록만 준다. 목록에 없는 숫자나 문제를 쓰지 않게 한다.

## 6. HS 코드 추천과 확정 (recommend_hs)

- 자동이 기본이고, 사람은 예외만 본다. 다만 AI 혼자 확정하지 않는다. 자동 확정은 근거 두 개가 맞을 때만 코드가 한다. HS 코드는 관세율과 수입 요건을 정하고, 틀리면 신고한 사람이 책임진다.
- 송장의 HS 는 6자리이거나 수출국 기준인 경우가 많다. 앞 6자리만 세계 공통이고, 수입신고서에는 한국 10자리(HSK)가 필요하다. 그래서 아래 auto_match 는 드물고, 실제 자동화는 확정 이력에서 나온다(같은 수입자의 같은 품목은 두 번째부터 자동). 발표의 자동 처리율도 이 경로로 보여 준다.
- 순서 (품목마다)
  1. 확정 이력(team06-hs-history)을 먼저 찾는다. 키는 수입자 + 품목 코드이고, 품목 코드가 없으면 수입자 + 정규화한 품명이다. 있으면 그 HS 로 자동 확정한다(`by: history`).
  2. 없으면 모델이 서류의 품명 · 재질 · 용도 칸에서 검색어를 뽑는다(한글 · 영문 동의어 포함). 검색어만 내고 HS 코드는 내지 않는다.
  3. 코드가 관세청 HS부호 표(CSV, 한글 · 영문 품목명 포함)에서 그 검색어로 후보를 찾는다(최대 30개). 서류에 HS 가 적혀 있으면 그 앞 6자리 아래의 10자리 코드도 후보에 넣는다.
  4. 모델이 그 후보 안에서 최대 3개를 고르고, 이유를 서류의 어느 칸에 근거했는지와 함께 쓴다. 후보 목록 밖의 코드는 버린다.
  5. 코드가 확정 여부를 정한다.
- 자동 확정(`by: auto_match`)은 아래를 모두 채울 때만 한다.
  - 서류에 10자리 HS 가 적혀 있고, HS 가 적힌 서류끼리 같다
  - HS부호 표에 있는 코드다
  - 모델 추천 1순위와 같다
- 그 밖에는 '사람 확인 필요'로 후보 3개를 화면에 넘긴다. 예: 서류에 HS 가 없음, 서류끼리 다름, 추천과 어긋남, 6자리만 있어 10자리 후보가 여럿.
- 사람이 고르면(`POST /jobs/{id}/hs`, `by: human`) 코드가 신고서 초안을 다시 채우고 확정 이력에 저장한다. 같은 수입자의 같은 품목은 다음부터 자동 확정된다. 모델 호출은 없다.
- 서류에 적힌 HS 와 추천 1순위가 앞 6자리에서 다르면 '확인 필요'로 리포트에도 올린다.
- 수출입실적 API 는 "이 코드로 실제 거래가 있는가"를 보여 주는 참고로만 쓴다. 확정 조건에 넣지 않는다.

## 7. 신고서 초안 (draft_declaration)

- 신고서는 코드가 템플릿에 값을 채워 만든다. 모델이 신고서 내용을 쓰지 않는다.
- 핵심 칸만 있는 간이 양식으로 시작한다. 칸 목록과 칸마다의 출처(어느 서류의 어느 칸)는 docs/schema.md 에 둔다.
- 칸마다 출처를 함께 남긴다. 확인 필요나 불일치가 남은 칸, 아직 확정되지 않은 HS 칸은 채우지 않고 표시한다.
- 초안에는 "사람 검토 전 초안"을 적는다. 실제 신고 전송은 하지 않는다.
- 초안은 화면에 표로 먼저 보여 준다. PDF 는 여유가 있을 때 만들고, 한글 PDF 는 글꼴 파일을 함께 넣어야 한글이 깨지지 않는다.

## 8. 시스템 연동 (push_to_wms)

- 실제 WMS · TMS · ERP 대신 가상 WMS(DynamoDB 테이블과 API 하나)를 둔다. 연동 코드는 어댑터 하나로 감싸서, 실제 시스템은 어댑터만 바꾸면 되게 한다.
- push_to_wms 는 에이전트 도구 목록에 넣지 않고 코드만 부른다. 외부 시스템에 쓰는 일은 AI 가 하지 않는다.
- 자동 등록(`by: auto`): 불일치와 확인 필요가 하나도 없고 모든 품목의 HS 가 확정되면, finish_report 가 결과를 저장한 직후 코드가 바로 등록한다. 사람이 HS 를 고른 뒤에도 같은 조건을 다시 검사해서, 다 채우면 바로 등록한다.
- 예외: 확인 필요가 남았으면 사람이 화면에서 승인할 때(`POST /jobs/{id}/approve`, `by: human`) 등록한다. 불일치가 남은 건은 승인해도 등록하지 않는다(409). 서류를 고쳐 다시 올려야 한다.
  - 판독 오류 예외: 서류는 맞는데 판독이 틀려 불일치가 난 건은, 검수자가 원본을 직접 보고 사유(`override_reason`)를 적어 승인하면 등록한다. 사유는 WMS 상태 · 단계 기록 · 검수 완료서에 남는다. 코드가 판정을 바꾸지는 않는다(불일치는 그대로 남고, 사람이 책임지고 넘긴 것이 기록된다).
- 같은 건이 두 번 들어가지 않게 멱등 키(B/L 번호 + 작업 ID)를 쓴다. 재시도해도 한 번만 들어간다.
- ERP 용 CSV 내보내기는 같은 검증 데이터로 만든다.

## 9. 현황 조회 (현황 Agent, #257)

- 현황 Agent 는 읽기 도구를 고르고, 앞 대화를 이어 받고, 도구 결과로 답을 쓴다. 조회 · 집계 · 정렬 · 날짜 계산 · 그래프 값은 코드(도구)가 한다. 자유 SQL 이나 코드를 만들게 하지 않는다.
  - 도구: `query_shipments`(조건으로 찾기) · `count_shipments`(상태 · 수입자 · 품목 · 일 · 주 · 월별 건수) · `make_chart`(그래프) · `get_job` · `find_jobs` · `list_documents` · `delay_rule`. 모두 읽기만 한다. 쓰기 도구(WMS · HS 이력 · 승인)는 넣지 않는다(8번).
  - 그래프: 모델은 종류(bar · line · pie)와 그릴 집계(`count_shipments` 결과의 source)만 고른다. 값 · 축 · 제목은 코드가 집계에서 채우고, 화면은 계산 없이 그린다. 집계가 없거나 0건이면 그래프를 만들지 않는다.
  - 앞 대화: 같은 session_id 의 최근 3턴(질문 · 답 · 쓴 조건 · 건수)을 team06-chat 에서 읽어 데이터로 넘긴다. '그중', '그 B/L' 은 앞 조건과 결과로 푼다.
  - 답 검사: 답에 나온 숫자와 B/L 번호 · 작업 ID 같은 낱말이 질문 · 앞 대화 · 도구 결과에 모두 있어야 모델 답을 쓴다. 없으면 코드의 문장틀 답으로 바꾼다. 화면 표(`rows`) · 조건(`filters`, `period_resolved`) · 그래프(`chart`)는 코드 결과 그대로다.
  - 한도: 모델 호출 4턴, 새 호출은 14초까지, 모델 읽기 타임아웃 8초(재시도 1회), 도구는 5초(재시도 1회). API Gateway 30초 안에 기록까지 끝낸다.
  - 켜고 끄기: 환경 변수 `QUERY_AGENT=1`. 끄면(또는 Agent 가 도구 결과 없이 실패하면) 조건 변환(모델은 조건 JSON 만, 답은 문장틀)으로 답한다.
- 기간은 `today` · `this_week` · `last_week` · `this_month` · `last_month` · 날짜 범위 중 하나로 받는다. "이번 주"가 며칠부터 며칠인지는 코드가 한국 시간으로 계산한다. 모델이 날짜를 계산하지 않는다.
- '통관 지연' 같은 상태는 코드 규칙으로 정한다. 예: 입항 후 정해 둔 일수가 지나도 수리되지 않은 건. 기준은 관세 규칙 담당이 정하고, 답에 함께 보여 준다.
- 답에는 조회 결과에 있는 건만 쓴다. 건수는 코드가 센 값을 쓴다. 0건이면 0건이라고 답하고 쓴 조건을 보여 준다.
- 현황 데이터는 처리한 작업과 미리 넣어 둔 가상 화물 기록(50~100건)이다. 작업이 끝나면 finish_report 가 화물 기록(team06-shipments)에 한 줄을 넣고, WMS 에 등록되면 상태를 고친다.

## 10. 모델 호출

- 어떤 모델을 쓸지는 정해 두지 않는다. 모델 ID 는 코드에 적지 않고 환경 변수(`MODEL_ID`)로 바꾼다.
- 첫날, 쓰기로 한 모델로 한 번 호출해 세 가지를 확인한다: 아래 1번 구조화 출력이 도는지, 도구 호출이 되는지, 서류 한 장을 읽는 시간.
- 형식을 받는 방법은 아래 순서로 정한다. 어느 쪽이든 받은 결과는 Pydantic 으로 검증한다.
  1. Strands 구조화 출력(`structured_output_model`). strands-agents 1.62.0 부터는 도구 강제 호출 → Bedrock 구조화 출력(Converse `outputConfig.textFormat`) → auto 순서로, 모델이 거절하지 않는 첫 방법을 알아서 쓴다. Bedrock 구조화 출력은 2026-10-19 부터 모든 Claude 모델에서 되고, botocore 1.42.42 이상이어야 넘길 수 있다.
  2. 1번이 안 되면 그 호출만 boto3 `converse` 에 `outputConfig.textFormat`(JSON 스키마)을 넣어 직접 부른다.
  3. 그래도 안 되면 도구를 auto 로 두고 언제 그 도구로 답하는지 프롬프트에 적거나, JSON 텍스트로 받는다.
- requirements 에 `strands-agents>=1.62.0` 과 `boto3` · `botocore` 1.42.42 이상을 적는다. Strands 1.61 이하는 구조화 출력에 도구 강제 호출을 써서 Opus 5.5 · Sonnet 5.5 에서 400 이 날 수 있다. Lambda 런타임에 든 boto3 는 이보다 낮을 수 있으니 배포 패키지에 같이 넣는다.
- 구조화 출력 스키마: 모든 object 에 `additionalProperties: false`. 필수가 아닌 속성은 전체 12개까지라, 넘으면 required 로 두고 null 을 허용한다. `minimum` · `maxLength` 같은 수치 · 길이 제약은 못 쓴다. Pydantic 모델에 dict · tuple 필드를 두면 Strands 가 Bedrock 구조화 출력을 건너뛰고 auto(형식 보장 없음)로 떨어지니 쓰지 않는다. 처음 쓰는 스키마는 컴파일에 최대 약 90초 걸리므로 읽기 타임아웃을 120초 이상으로 둔다.
- Claude 5.5 계열을 쓴다면 아래를 지킨다.
  - temperature · top_p · top_k 를 넣지 않는다. Opus 5.5 는 넣기만 해도 400, Sonnet · Haiku 5.5 는 기본값이 아닌 값이면 400 이다. 강의 예시 코드의 `temperature=0.3` 도 지운다.
  - 도구 강제 호출(tool_choice 의 any 나 도구 지정): Sonnet 5.5 · Opus 5.5 는 400 이다. Haiku 5.5 는 받는다. 모델을 바꿔도 되게 도구는 auto 로 둔다.
  - 응답 앞부분을 미리 채우는 prefill 은 오류다. 메시지는 사용자 턴으로 끝낸다.
  - 응답 앞에 생각(thinking) 블록이 올 수 있다. 구조화 출력의 JSON 도 생각 블록 뒤의 text 블록에 온다. `content[0].text` 처럼 위치로 읽지 말고 블록 종류로 읽는다.
  - `max_tokens` 는 생각까지 포함해 넉넉히 둔다. 속도는 생각을 끄지 말고 effort 를 낮춰 조절한다(기본값: Opus 5.5 · Haiku 5.5 는 medium, Sonnet 5.5 는 high).

## 11. 평가 (eval/)

- 정답지 형식은 docs/schema.md 의 약속 3 을 따른다. CSV 한 줄에 심은 오류 하나를 적고, 정상 세트는 `error_type=none` 한 줄로 적는다. 서류 종류와 품목별 HS 정답은 `eval/sets.csv`, 핵심 칸의 정답 값은 `eval/fields.csv`(세트, 서류, 칸, 정답), 현황 조회 질문은 `eval/queries.csv` 에 둔다.
- P0 대조는 서류 전체 값만 비교하므로, 정답지의 `field` 는 서류 전체 값 이름(`total_qty` · `total_gross_kg` · `invoice_no`)이다. `invoice_no` 는 약속 1 의 `doc_no` 다. 합계가 찍히지 않은 서류(스타일 2 상업송장의 여러 줄 수량)는 줄 값을 코드가 더한다. 행 단위 칸(`items[0].gross_kg`)은 행 맞추기를 하는 P1 부터 쓴다. 채점할 때 issues 의 cells 가 행 단위로 짚었으면(약속 2 예시의 `items[0].gross_kg`) 같은 서류의 전체 값 이름으로 묶어 센다.
- 주최 측 데이터가 없어서 데이터셋은 생성기로 만든다(samples/generate_dataset.py). 세트마다 상업송장 · 포장명세서 · B/L · 원산지증명서(약 80%)가 있다. 상업송장 · 포장명세서 양식은 공개된 실제 서류(KOTRA 수출 가이드북, Shipping Solutions, refs/sources.csv), B/L 은 BIMCO CONLINEBILL, 원산지증명서는 한-중 FTA 부속서 3-C · Form AK · Form VK 의 칸 구성을 따른다. 값(거래처 · 품목 · 수량 · 심는 오류)은 samples/RULES.md 의 규칙으로 만든다. 회사명 · 주소 · 번호는 모두 가상 값이고, 모든 서류에 SAMPLE 을 찍는다. 정답 HS 와 헷갈리는 HS 는 관세청 HS부호 표에서 확인한 10자리다.
- 정답지는 서류를 만들 때 build_samples.py 가 함께 쓴다(생성기가 적은 오류를 양식 계산 값과 맞춰 본 뒤). check_samples.py --docs 가 서류를 다시 읽어(PDF 글자층, 그림 OCR) 정답 값이 실제로 찍혔는지, 품명이 잘리지 않았는지 확인한다.
- 규모는 125세트 479장이다(개발용 75, 발표용 50). 발표용에는 P0 심은 오류 20건 이상, 정상 10세트 이상이 있다. 개발 중에는 개발용 일부로 돌리고, 전체는 마지막에 한 번 읽은 뒤 판독 캐시로 규칙만 바꿔 다시 채점한다. 매번 전체를 모델로 읽으면 크레딧과 시간이 많이 든다.
- 텍스트 PDF 만으로 점수를 내지 않는다. 상업송장 · 포장명세서의 25%는 PNG, 30%는 스캔본(기울기 · 흐림 · 잡티가 있는 글자층 없는 PDF)이고, B/L 은 40%, 원산지증명서는 55%가 스캔본이다. 형식별 점수를 따로 낸다(eval/sets.csv 의 fmt_a~fmt_d). 현장에 프린터가 있으면 몇 장은 출력해서 휴대폰으로 찍어 점수를 따로 낸다. 깨끗한 PDF 만으로 낸 점수는 실제보다 좋게 나온다.
- '잘 읽었다'는 서류의 핵심 칸이 모두 정답과 같을 때다. 칸별 정답 수도 함께 낸다.
- 정답지의 절반 가까이는 오류 없는 정상 세트로 둔다. 오탐은 정상 세트에서 센다. 정상 세트의 약 45%에는 달라 보이지만 오류가 아닌 차이(`variant`: 원산지증명서 품명 오타, 반올림, 소급 발급 표시 등)를 넣었다. 여기서 불일치를 내면 오탐이고 '참고'는 괜찮다. variant 별 오탐 수도 낸다.
- P0 채점은 정답지의 `phase=P0` 줄만 정답으로 보고, P0 줄이 없는 세트는 P0 기준 정상 세트로 센다.
- 탐지는 심은 칸(`doc`, `field`)을 짚었을 때만 센다. 엉뚱한 칸을 짚어 세트가 걸린 것은 탐지가 아니다. 서류 두 장의 대조라면 짚은 두 칸에 심은 칸이 들어 있으면 탐지로 센다.
- 기능별로 따로 잰다.
  - 분류: 서류 종류 정답 수
  - 읽기: `eval/fields.csv` 로 잰 칸별 판독 정답 수. 탐지가 낮을 때 읽기 문제인지 규칙 문제인지 가를 수 있다
  - 판정: 위의 탐지와 오탐
  - HS: 자동 확정한 건수와 그중 틀린 건수(0 이어야 한다), 사람에게 넘긴 건 중 정답 HS 가 후보 3개 안에 든 건수. 데이터셋 품목의 정답 HS 는 HS 표에서 사람이 골라 둔다
  - HS 함정: 품명에 결정 근거가 있는데 헷갈리는 HS 가 있는 품목(eval/sets.csv 의 `trap_hs`)에서 헷갈리는 쪽을 고른 수. 송장과 원산지증명서에 같은 헷갈리는 HS 를 적은 세트(`error_type=trap_all_docs`)에서 자동 확정이 틀린 HS 를 통과시키는지 본다. 통과시키면 자동 확정 조건을 좁힌다(예: 확정 이력만 자동). 발표용에는 개발용에 없는 함정 품목이 따로 있다
  - 자동 처리율: 정상 세트 중 사람 손 없이 WMS 등록까지 끝난 수. 같은 품목이 두 번 나오는 세트를 넣어 두 번째 건이 자동으로 끝나는지 본다
  - 신고서: 칸별로 정답과 같은 수. 비워 둔 칸은 틀림과 따로 센다
  - 현황 조회: 질문 20개의 기대 조건 · 기대 건수와 맞는 수
- 평가 스크립트는 '사람 확인 필요'가 나오면 정답지의 HS 를 사람이 고른 것처럼 넣고 계속 돌린다.
- 평가와 10회 반복은 확정 이력을 비운 상태에서 시작한다. 이력이 남아 있으면 실행할 때마다 결과가 달라진다.
- 세트를 개발용(dev)과 발표용(test)으로 나눈다. 프롬프트와 규칙은 개발용만 보고 고치고, 발표용은 마지막에 한 번만 돌린다. 발표용 입력 · 정답지 · 서류와 발표용 전용 품목 · 거래처는 git 에 올리지 않고(samples/data/*_test.csv, samples/gen/*_test.csv, eval/test/, samples/test/), 프롬프트를 고치기 전에 check_samples.py --lock-test 로 잠근다. 해시만 적은 samples/test_lock.json 을 커밋하고 태그를 달며, 그 뒤로는 고치지 않는다.
- 평가 스크립트는 저장된 판독으로 모델 호출 없이 다시 채점할 수 있어야 한다.
- 비교 기준선으로, 같은 정답지를 모델에게 세트째 주고 불일치를 찾게 한 결과도 한 번 잰다. 발표의 "모델 혼자 vs 우리 방식" 비교가 된다.
- 처리 시간은 팀원이 같은 세트를 직접 처리한 시간을 재서 Agent 처리 시간과 비교한다. 근거 없는 업계 수치를 쓰지 않는다.
- 결과는 건수로 쓴다. 예: "심은 오류 20건 중 17건 탐지, 정상 10세트 중 오탐 0건". 정상 세트가 적으면 '오탐률 0%'라고 쓰지 않는다.
- 리허설 때 같은 세트를 캐시를 끄고 10번 돌려 판정이 매번 같은지 기록한다.
